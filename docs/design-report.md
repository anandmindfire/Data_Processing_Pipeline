# Design report — Concurrent Data Processing Pipeline

The service is a single-process Go HTTP application with asynchronous jobs. A job specification describes CSV, JSON-file, or HTTP JSON sources; declarative validation and normalization rules; count/sum/average aggregations; and CSV/JSON export targets. The API validates the minimum job shape, persists a pending job, then executes it in the background under a per-job context and timeout.

The pipeline is a bounded channel graph. Each source has its own goroutine and sends typed `sources.Item` values to a shared raw channel. A configurable validation worker pool fans out from that channel and emits valid records to a second channel; invalid records go to a centralized error channel. A configurable transformation pool applies normalization and numeric conversion. A single fan-in collector consumes transformed records, persists them, and updates group aggregates. Single ownership of aggregation state avoids map races and removes the need for a lock in the hot aggregation path. Coordinators close channels only after their upstream worker groups finish, which prevents sends to closed channels. Bounded buffers provide backpressure rather than allowing unbounded memory growth.

`context.Context` is propagated into source readers and HTTP requests. Cancellation is cooperative: readers and workers stop at context-aware operations, coordinators wait for workers, and the API reports the terminal state. Errors are isolated by stage and retain source/index and failed-record details. Metrics distinguish discovered, processed, valid, rejected, exported, and failed records; throughput and timestamps are computed at completion.

The implementation uses an atomic JSON snapshot store to avoid an external database dependency while meeting the assignment's file-persistence option. This is deliberately a trade-off: it is easy to run and inspect, but rewrites state on updates, serializes writes, and supports one process only. A production multi-instance deployment should substitute PostgreSQL transactions, use object storage for large exports, add queue-based scheduling, authentication, SSRF/path controls, quotas, retention, and richer Prometheus histograms. The current aggregation engine keeps in-memory group state, so cardinality and record-count limits should be enforced for untrusted workloads.
